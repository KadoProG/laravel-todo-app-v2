## A. バリデーションは書いたが、条件が実際の操作と合っていない

### `10bd318` メールアドレスを変えないユーザー更新が 422 になる

`'email' => 'sometimes|string|email|max:255|unique:users'` としていたため、
自分の現在のメールアドレスを含めて PUT すると自分自身と衝突して失敗した。
`Rule::unique('users')->ignore($user->id)` に置き換えて解消。

**抜けていたもの**: 「更新」における一意制約は「作成」とは意味が違う、という考慮。
`unique` を書いた時点では新規登録の文脈しか想定されていなかった。

**気づけなかった理由**: ユーザー更新 API（`f23a14a`, 2025-04-14）にテストが無く、
発覚は約 2 年後のフロント連携時。

**関連**: 直後の `3248194` (#8) で `UpdateUserRequest` に分離し、認可（本人のみ）も追加している。
つまり最初の実装には**バリデーションの誤りと認可の不在が同時にあった**。

## B. バリデーションは通るが、保存処理が書かれていない

### `cc8ee38` タスク担当者が更新されない

`assigned_user_ids` をバリデーションルールに含めていたが、
`Task::create($validated)` / `$task->update($validated)` にそのまま渡していた。
多対多リレーションは `fillable` では処理されないため、値は黙って捨てられていた。

修正では `assigned_user_ids` を切り離し、`sync()` をトランザクション内で実行するようにした。

**抜けていたもの**: リレーション項目は「入力として受け付ける」だけでなく
「別経路で永続化する」必要がある、という対応付け。

**気づけなかった理由**: エラーにならず 200 が返るため、レスポンスだけ見ると成功に見える。
`TaskResource` が更新後の担当者を返していれば気づけた可能性がある。

## C. ルートモデルバインディングの変数名が一致していない

### `4c84855` タスクアクションの更新・削除が無反応

`apiResource('tasks/{task}/actions')` が生成するパスパラメータは `{action}` だが、
コントローラは `TaskAction $taskAction` で受けていた。
Laravel は名前が一致しないと解決せず、空のモデルに対して `update()` / `delete()` を呼んでいた。

**抜けていたもの**: ネストした `apiResource` が生成するパラメータ名の確認。

**気づけなかった理由**: 例外が出ず 200 / 204 が返る。テストが無かった。

**関連**: 同じルート定義は後に `4b6ef3d` (#16) でも「ルート名が URI から自動生成されて不自然」
という理由で手当てされている。**ネストした `apiResource` の自動生成に依存したことが 2 回問題になっている**。

## D. 依存更新に追従できていない

### `edbb75b` PHP 8.5 化の置き去り（#18 の 5 日後に発覚）

Dependabot がベースイメージを `8.3-fpm` → `8.5-fpm` に上げた（`5681426`, #18, 8/11）が、
以下が追従できておらず、まとめて 8/16 に修正された。

- `opcache` が 8.5 のイメージに同梱済みで、`docker-php-ext-install` に渡すとビルドが失敗する
- `composer.lock` の 3 パッケージが 8.5 の制約を満たさず `composer install` が解決できない
- `PDO::MYSQL_ATTR_SSL_CA` が非推奨になり、`Pdo\Mysql` への置き換えが必要
- **非推奨警告がレスポンス本文に混入し、JSON と CORS ヘッダを破壊していた**
- CI の PHP バージョンが `8.3` のままで、本番と CI が別のバージョンを走らせていた

**抜けていたもの**:

1. ベースイメージ更新 PR で「ビルドが通るか」以上の検証がされていない
2. `php.ini` を丸ごと差し替えているのに `display_errors` / `error_reporting` を明示しておらず、
   PHP 側の既定値の変化がそのままレスポンス破壊につながる状態だった
3. CI とランタイムの PHP バージョンを同期させる仕組みが無い

**教訓として明示的に残っている点**: 修正では `php.ini` に
`error_reporting` / `display_errors` / `log_errors` を明示し、
「警告がレスポンス本文に混入すると JSON も CORS ヘッダも壊れる」とコメントを残している。

## E. テストが実装に追随していない

### `a082d5a` テストコードの一括修正

以下が一度にまとめて直された。テストが**実装から数か月遅れで乖離していた**ことを示す。

- レスポンスが `tasks` / `task` キーでラップされる形に変わっていた
- キャメルケース（`isDone`）→ スネークケース（`is_done`）への変更が反映されていなかった
- エンドポイントが `/api/v1/me` → `/api/v1/users/me` に変わっていた
- SoftDeletes 導入後も `assertDatabaseMissing` のままだった（→ `assertSoftDeleted`）
- `is_public` が必須になったのにテストデータに含まれていなかった
- 一覧が作成者で絞られる前提になっていたのに、テストが無関係のユーザーのタスクを作っていた

同時にバリデーション境界のテスト（文字数上限、型、`assigned_user_ids` の要素存在確認、空配列許容）
が 9 件追加されている。**それまでバリデーションのテストがほぼ無かった**。

**抜けていたもの**: レスポンス形式やエンドポイントを変えた時点でテストを直す運用。
CI でテストが走るようになったのは `3063452` (#9, 2026-04) 以降で、
それ以前はテストが壊れたまま放置されても検知されなかった。

## G. ローカルでは再現しない、本番構成固有の抜け（4 件・すべて 1 日で発生）

AWS デプロイ環境の追加（`03b1012`, #24）以降、
**CloudFront → ALB → nginx → php-fpm という多段プロキシに起因する不具合が 4 件連続**した。

### 発生順

1. **`a3c0c83` (#30)**: ALB は自身が HTTP で受けるため `X-Forwarded-Proto` に `http` を入れる。
   実際のプロトコルは非標準の `CloudFront-Forwarded-Proto` にしかなく、Laravel は解釈できない。
   結果、未認証時のリダイレクト先が `http` になり混在コンテンツ扱いになった。
   → nginx で両者をマッピングして解決（**フロント側の CloudFront 設定と両方揃わないと直らない**）
2. **`c3c5bab` (#31)**: `EnsureFrontendRequestsAreStateful` が、
   `FRONTEND_URL` から導出した stateful ドメインと Origin が一致するとセッション認証扱いにして
   CSRF 検証を要求する。API とフロントを同一オリジンで配信する本番では必ず一致し、419 になっていた。
   **ローカルはフロント `:5173` / API `:8080` でオリジンが異なるため表面化しなかった。**
   → 認証は JWT のみでセッション不使用のためミドルウェアごと削除
3. **`e446fc4`**: 1 の対処で `X-Forwarded-Proto` を `https` に直した一方、
   `X-Forwarded-Port` は ALB のリスナーポート（80）のまま。
   scheme とポートが食い違い `https://<host>:80/...` が生成され、`ERR_SSL_PROTOCOL_ERROR` になった。
4. **`97c01bf` (#38)**: 上記の**対症療法の連鎖そのものをやめる**判断。
   絶対 URL を生成しているのは `UserResource` の 1 箇所だけなのに、
   nginx がヘッダを書き換え → Laravel が解釈 → ポートの食い違いを別の細工で埋める、
   という連鎖ができていた。公開先は CloudFront の 1 つに固定なので `APP_URL` をそのまま使う形に統一。
   `trustProxies` はクライアント IP 復元（ログイン試行のレート制限キー）のためだけに残した。

### 抜けていたもの

- **ローカルと本番で前提が違う箇所の洗い出し**。特に「オリジンが同一か別か」「プロキシが何段あるか」。
  #31 は、ローカルでオリジンが分かれていたことが逆に問題を隠していた。
- **プロキシ越しのリクエストを模したテスト**。`e446fc4` と `97c01bf` で
  `X-Forwarded-Proto` / `X-Forwarded-Port` / `X-Forwarded-Host` を付けたテストが初めて追加された。
- **絶対 URL の生成方針を決めておくこと**。決めていなかったため、
  リクエストヘッダから公開 URL を復元する方式に流れ、段階的に破綻した。
- 3 は 1 の修正が引き起こしている。**環境差分の対処を場当たりに重ねると、次の不具合を作る**。

## 同じ類型でまだ塞がっていない箇所

過去の fix と同じ種類の抜けが、現在のコードにも残っている。
いずれも「エラーにならないため気づきにくい」という点で A / C と同型。

### 1. タスクの更新・削除に所有者チェックが無い

`UpdateTaskRequest::authorize()` は `$this->user() !== null` を返すだけで、
`TaskController::destroy()` に至っては FormRequest すら通していない。
**認証さえ通れば他人のタスクを更新・削除できる。**
`10bd318` / `3248194` (#8) でユーザー更新に本人チェックを入れたのと同じ対処が必要。

- [app/Http/Requests/UpdateTaskRequest.php:9](../app/Http/Requests/UpdateTaskRequest.php#L9)
- [app/Http/Controllers/v1/TaskController.php:78](../app/Http/Controllers/v1/TaskController.php#L78)

### 2. タスクアクションの一覧・削除に認可が無い

`store` / `update` は FormRequest の `authorize()` で作成者または担当者に限定しているが、
`index` と `destroy` は素の `Request` で受けており、チェックが無い。

- [app/Http/Controllers/TaskActionController.php:41](../app/Http/Controllers/TaskActionController.php#L41)

### 3. ネストしたルートに `scopeBindings()` が無い

`tasks/{task}/actions/{action}` で、`{action}` が `{task}` に属するかを検証していない。
他タスクのアクション ID を指定すると、そのまま解決されて操作できる。
`4c84855` で問題になったのと同じルート定義。

- [routes/api.php:25](../routes/api.php#L25)

### 4. タスク一覧・詳細に公開範囲の絞り込みが無い

`TaskController::index()` は `scopeFilter` によるフィルタのみで、
所有者や `is_public` による絞り込みをしていない。`show()` も同様。
`a082d5a` のテストが `created_user_id` と `is_public => false` を明示するよう直された経緯から、
当時は絞り込む前提だった可能性がある。仕様として意図的かどうかの確認が必要。

- [app/Http/Controllers/v1/TaskController.php:18](../app/Http/Controllers/v1/TaskController.php#L18)
